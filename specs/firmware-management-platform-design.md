# 固件资源管理平台设计

> 基于当前 `firmware-flash-automation` 项目现状整理。
>
> 日期：2026-04-29

---

## 1. 现状判断

当前项目已经不是单纯的“手控刷机脚本”，而是一个已有雏形的桌面工具平台：

- 已有统一窗口壳：`UnifiedFlashPlatform`
- 已有两类流程：`handcontrol`、`music`
- 已有目录扫描、搜索、双击打开原目录、U 盘刷写、串口操作、资源详情展示
- 现有问题不是“能不能做”，而是“领域模型还停留在手控工具阶段”

现在的核心限制：

1. 扫描规则只适配手控目录，无法覆盖 19 类固件
2. 列表条目只有 `model/version/path`，没有“固件类型、刷写方式、关联工具”
3. 刷机动作和“资源管理动作”混在一个面板里
4. 不同固件类型的刷写方式不同，但项目里还没有“按类型分派动作”的结构
5. 新增固件、修改目录、查找工具，仍然依赖人工点文件夹

结论：

这个项目适合继续演进，但目标应该从“手控 UI 刷机工具”升级为“固件资源管理平台”。

---

## 2. 目标定义

平台目标不是把所有固件都做成同一种自动刷机，而是统一做三件事：

1. 管理固件烧录包
2. 快速定位原始目录和工具
3. 按固件类型执行对应动作

对应到实际使用，应支持以下场景：

- 按型号、版本、固件类型搜索
- 列表展示一个型号下的全部固件集合
- 双击打开原始目录
- 一键打开该类型对应的刷机工具
- 对支持自动化的类型执行自动流程
- 对不支持自动化的类型，至少能做“打开目录 + 打开工具 + 显示操作说明”

这比“所有类型都自动刷机”更现实，也更适合当前公司目录现状。

---

## 3. 产品形态建议

建议将程序定义为：

`固件资源管理平台 + 按类型工具启动器 + 部分类型自动刷机器`

不要把所有类型都塞进“手控模式 / 音乐模式”这种 UI 切换里，下一阶段更合适的结构是：

- `资源总览`
- `固件列表`
- `详情与操作`
- `工具中心`

### 3.1 资源总览

显示：

- 扫描根目录
- 总型号数
- 总固件包数
- 各固件类型数量
- 最近更新目录

### 3.2 固件列表

每一条记录不再只是“一个手控目录”，而是一个固件资源条目，至少包含：

- 型号
- 版本
- 固件类型
- 目录名
- 文件名
- 刷写方式
- 关联工具
- 状态标签

支持过滤：

- 型号
- 版本
- 固件类型
- 是否支持自动刷机
- 是否有工具入口

### 3.3 详情与操作

选中条目后，右侧显示：

- 原始路径
- 识别出的固件文件
- 兼容型号
- 使用说明
- 工具路径
- 最近修改时间

可执行动作：

- 打开目录
- 复制路径
- 打开刷机工具
- 执行自动刷机
- 编辑备注
- 标记“已验证 / 待确认 / 废弃”

### 3.4 工具中心

工具中心单独维护，不再让用户自己进目录找：

- 手控刷机工具
- 音乐固件工具
- 主板烧录工具
- 蓝牙工具
- 语音工具
- 其他第三方 EXE / BAT / 文档

每个工具项至少要有：

- 名称
- 适用固件类型
- 工具路径
- 启动参数
- 备注

## 4. 领域模型建议

当前 `FirmwareType = Literal["handcontrol_ui", "music_bt"]` 太窄，建议改成可扩展模型。

### 4.1 固件类型枚举

第一阶段建议至少覆盖：

- `mainboard`
- `handcontrol_ui`
- `bluetooth`
- `voice`
- `shortcut_key`
- `movement_3d`
- `movement_2d`
- `knob_switch`
- `leg_unit`
- `knee_unit`
- `audio_board`
- `health_module`
- `commercial_mainboard`
- `seat_reminder`
- `card_reader`
- `leroyao`
- `triple_module`
- `aging`
- `segment_display`
- `music_bt`

### 4.2 资源条目

建议新增统一对象，例如：

```python
class FirmwareAsset(TypedDict):
    asset_id: str
    firmware_type: str
    model: str
    version: str
    path: str
    folder_name: str
    files: list[str]
    flash_mode: str
    tool_name: str
    tool_path: str
    notes: str
    compatible_models: list[str]
```

### 4.3 刷写方式

建议不要直接把逻辑写死到 UI，先抽象刷写方式：

- `auto_usb`
- `auto_serial`
- `tool_launch`
- `manual_doc`
- `disabled`

这样 UI 只负责根据类型显示按钮，服务层负责具体执行。

## 5. 扫描规则建议

你现在已经有 `config.toml`，下一步不要把不同固件类型继续写死在 Python 里，应该把识别规则配置化。

建议新增独立配置，例如：

`config/firmware_catalog.toml`

结构示意：

```toml
[[firmware_types]]
key = "handcontrol_ui"
label = "手控UI"
dir_keywords = ["手控", "手控UI", "手控器"]
file_extensions = [".rom", ".pkg", ".zip", ".bin"]
flash_mode = "auto_usb"
tool_name = "手控刷机"
tool_path = ""

[[firmware_types]]
key = "mainboard"
label = "主板程序"
dir_keywords = ["主板", "主板程序"]
file_extensions = [".bin", ".hex"]
flash_mode = "tool_launch"
tool_name = "主板烧录工具"
tool_path = ""
```

扫描过程建议改成两层：

1. 先识别目录属于哪种固件类型
2. 再按该类型规则提取型号、版本、文件集合

这样以后新增固件类型时，优先改配置，不优先改代码。

## 6. UI 改造建议

当前 UI 已经具备基础框架，不建议推倒重写，建议重组为三块。

### 6.1 左侧

从“模式切换 + 列表”改成：

- 搜索框
- 固件类型筛选
- 刷写方式筛选
- 状态筛选
- 资源列表

### 6.2 中间

显示条目详情：

- 型号
- 版本
- 固件类型
- 文件清单
- 路径
- 最近更新时间

### 6.3 右侧

显示可操作按钮：

- 打开目录
- 打开工具
- 自动刷机
- 打开说明文档
- 标记状态

现在的“手控面板”和“音乐面板”不需要立刻删除，可以先改成：

- 通用资源面板
- 手控专用操作卡
- 音乐专用操作卡

也就是共用列表和详情，按固件类型动态显示不同操作区。

## 7. 代码改造顺序

建议按下面顺序做，避免返工。

### 阶段 1：先把“手控扫描”改成“通用资源扫描”

新增：

- `core/catalog.py`
- `core/services/catalog_service.py`

替代当前只返回 `HandcontrolFolder` 的方式，统一返回 `FirmwareAsset`。

阶段目标：

- 手控、音乐先纳入统一列表
- 每条记录带 `firmware_type`
- UI 搜索从“手控目录”升级为“固件资源列表”

### 阶段 2：引入“工具中心”

新增：

- `config/tools.toml` 或 `data/tools.json`
- `core/services/tool_registry_service.py`

能力：

- 记录每类固件对应工具
- 列表中一键打开工具
- 不需要再手动去目录找 EXE

### 阶段 3：按类型分派动作

新增统一入口：

- `run_flash_action(asset, drive)`
- `open_flash_tool(asset)`
- `open_asset_folder(asset)`

其中：

- 手控继续走现有 `run_one_click`
- 音乐继续走现有 `run_music_flash`
- 其他类型先走 `tool_launch`

这样项目马上就能覆盖更多固件类型，即使暂时不做自动化。

### 阶段 4：建立“型号视图”

当前列表是“目录视图”，后续建议补一个“型号视图”：

- 一个型号下聚合显示全部固件类型
- 可以看到该型号是否缺少某类固件
- 更符合实际出货前 5~13 个板卡成组管理的需求

## 8. 对当前仓库的直接建议

短期内，不建议先做这些事：

- 不建议先重写为 Web 系统
- 不建议先接数据库
- 不建议先做复杂权限系统
- 不建议先追求所有固件自动刷机

短期最值得做的是：

1. 扫描模型泛化
2. 固件类型配置化
3. 工具中心
4. 列表统一展示全部固件资源

这是最小投入、最高收益的路线。

## 10. 最终判断

这个项目可以继续用，而且方向是对的。

但下一步不该继续围绕“手控工具补功能”，而应该转成：

`固件资源管理平台`

也就是：

- 手控刷机功能保留
- 音乐功能保留
- 其他固件先接入“搜索、定位、打开工具”
- 自动刷机按类型逐步补齐

这样你马上就能解决现在最痛的两个问题：

1. 不用再一层层目录手动找文件
2. 不用再靠人工记住每种固件用哪个工具

后续如果继续实现，建议第一刀先改扫描与数据模型，不要先改视觉层。
