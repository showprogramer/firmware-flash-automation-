# Agent 工作流

`AGENTS.md` 是共享入口，`CLAUDE.md` 只做兼容引用。本文定义留档与验收规则。

## 执行与沟通

1. 查看工作区差异，按当前任务读取相关代码、测试和规格；仅需更新变更记录时读取 CHANGELOG 的 Unreleased。
2. 需求明确就执行，合理的小决定自行处理。只有影响结果的歧义、缺失信息或未获授权的操作才询问。
3. 按改动范围验证；通过后不重复运行相同检查，除非又有改动、失败或未解决问题。
4. 回复给出结果、必要验证及待办。无新信息不重复进度；不逐条播报工具调用，不用固定总结模板凑内容。

## 什么时候留档

| 内容 | 创建或更新条件 | 保留内容 |
| --- | --- | --- |
| Task：`specs/active/TASK-YYYYMMDD-short-name.md` | 跨模块、多阶段、存在待决规则或需跨会话接手 | 当前目标、规则、验收清单、状态、最新验证与阻塞 |
| Review：`docs/code-review/REVIEW-YYYYMMDD-short-name.md` | 重大重构、公共 API、schema、扫描索引、USB、服务契约或 UI 入口改动 | 有证据的问题、影响、处理结论及剩余风险 |
| CHANGELOG：`docs/CHANGELOG.md` | 用户可感知功能、重要缺陷修复、兼容性或安全变化 | 用户能观察到的结果 |
| 迁移说明：`docs/migrations/` | 路径、公共入口、配置/runtime 路径、schema 或兼容层变化需要交代迁移方式 | 受影响对象、迁移步骤、兼容性及必要恢复方式 |
| 架构决策：`specs/decisions/` | 实际形成需要长期保留的架构决策 | 决策、关键理由与约束 |

单次小修、纯文档和测试补齐可直接执行，在最终回复写结果与验证，不为走流程新增 Task 或 Review。有现成 Task 时更新原文。

- 需求变化直接改规则和验收；删除作废内容，不追加修订史、旧方案或审查轮次统计。
- 验收标准与 DoD 合成一份勾选清单；不另设“DoD 已更新”这类自指检查项。
- 不强制复杂度标签或理由；任务过大时按可独立验收的结果拆分，并说明依赖。
- 不保存重复文件列表、分支、提交 hash、固定平台列或无意义的“不适用”章节。Git 保存变更历史。
- 验证保留每条必要命令的最新结果；失败、未执行项和未解决限制不能被旧的通过记录掩盖。
- 必需项全部完成后，Task 移到 `specs/archive/`；Review 议题关闭且相关改动合入后移到 `docs/code-review/archive/`。只更新已有且受影响的索引，不为归档另建报告。
- 历史归档只按需查阅，不为新格式批量改写。运行截图放 `docs/ui-reference/screenshots/`，设计草图放 `specs/design/sketches/`。

## Task 最小格式

```markdown
# TASK-YYYYMMDD-short-name：任务名称

状态：进行中 / 实现完成，等待人工验证 / 已完成

## 目标与规则

写当前行为、必要约束及范围边界；已有规格用链接引用。

## 验收清单

- [ ] 可观察、可验证的结果

## 验证

- 自动化：命令 → 最新结果。
- 人工：具体验证场景与结论；待验证时写最短操作步骤。
- 文档：Review、CHANGELOG、迁移说明的结果与链接；不适用项合并说明。

## 待决事项

仅在有未决问题或阻塞时保留，写清需要什么信息或操作。
```

不适用的自动化或人工验证用一句话说明原因；Review、CHANGELOG、迁移说明可合并为一行“不适用（原因）”。不创建空表格，不预填通过结果。状态与验收清单必须一致；需要人工验证的任务，用户尚未确认时不写“已完成”。

## 验证与提交

Python 代码验证使用 `AGENTS.md` 的命令。纯文档只检查差异、链接及规则一致性；其他改动运行对应检查。未验证就明确写未验证。

以下改动必须在提交前获得用户“验证通过”的确认：

- UI、操作面板注册表或 UI 入口；
- core 公共 API、类型/服务契约、schema；
- 固件资产、扫描索引、USB、配置、性能或安全边界；
- 重构与新功能。

无 UI 可操作时，Agent 可用独立临时目录中的一次性场景脚本验证，不触碰真实用户数据。记录执行命令、场景和结果，仍须用户确认后提交。涉及 UI 或现场行为的改动须用户实机验证。

执行顺序：

1. 实现并完成适用的自动化检查；有 Review 要求时处理阻断问题。
2. 需要人工验证时给出最短验收步骤，回复“实现完成，等待人工验证”。
3. 用户确认后更新验收、状态和适用文档，回复“人工验证通过，记录已更新”。同一会话已有确认时不重复询问。
4. 已获提交授权且必需项完成后，检查本次差异和暂存范围，按 [提交格式](COMMIT_TEMPLATE.md) 提交。用户既有改动不混入本次提交。
5. 提交后报告 hash 即可；不回填 Task 的完成 hash，不为记录 hash 追加收尾提交。

`scripts/check_task_sync.py` 和包含它的 `scripts/test.ps1` 仍面向旧 Task 表格，属于旧格式的按需检查工具，不再作为新格式提交门槛。新任务使用上面的命令与清单检查；不要为满足旧脚本重新加入已取消的字段。

## Review 与 CHANGELOG

Review 只记录能定位、能说明实际影响的问题；未决设计只在影响当前验收时阻断。修复后复核相关问题，无新证据不重复整轮审查，不要求为了凑格式产生问题或额外报告。

CHANGELOG 使用 Keep a Changelog：待发布内容放 Unreleased，按实际内容选择 Added / Changed / Fixed / Removed / Deprecated / Security。同一功能合成一条结果描述，不复制 Task、Review 或提交流水账；纯格式化、类型标注、内部重构、测试和流程调整不写入。

## 本地内容与忽略规则

- 不默认读取或共享真实配置、公司内部资料、办公文件、运行缓存、原始会话或私人提示词；配置参考 `config.example.toml`，需要真实值时由用户提供相关片段。
- USB 设备、路径和序列号使用 `<USB_DRIVE>` 等占位符；个人草稿放 `.local/ai-prompts/`。
- `.codex/`、`.qoder/`、`.local/` 由 Git 和 Agent ignore 排除。
- 修改 `.claudeignore`、`.codexignore` 或 `.cursorignore` 时同步三份文件，仅保留顶部工具名称注释的差异。
